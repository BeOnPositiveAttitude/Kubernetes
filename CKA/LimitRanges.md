Объект `LimitRange` в Kubernetes - это политика, которая управляет распределением ресурсов (CPU, память, хранилище) на уровне namespace. Его главная цель - не дать отдельным контейнерам или pod-ам монополизировать все ресурсы namespace, а также гарантировать, что каждый pod получит минимально необходимый объем ресурсов.

В отличие от `ResourceQuota`, который ограничивает общее потребление ресурсов всем namespace, `LimitRange` устанавливает ограничения и значения по умолчанию для **каждого отдельного объекта** (pod, container, pvc).

### Назначение полей `spec.limits`

Все правила, которые устанавливает `LimitRange`, описываются в поле `spec.limits`. Это массив, в котором каждый элемент (`LimitRangeItem`) определяет набор ограничений для определенного типа объекта (`type`). Для каждого типа можно задать несколько ключевых полей.

Вот таблица с основными полями `spec.limits` и их значением:

| Поле | Назначение | Применимо для типов |
| :--- | :--- | :--- |
| **`type`** | **Определяет тип объекта**, к которому применяются правила. Основные значения: `Container`, `Pod` и `PersistentVolumeClaim`. | Обязательное поле для каждого элемента массива. |
| **`max`** | **Устанавливает максимальное значение** ресурса. Для `Container` это максимум для одного контейнера, для `Pod` — суммарный максимум для всех его контейнеров. Превышение этого значения при создании Pod'а вызовет ошибку. | `Container`, `Pod`, `PersistentVolumeClaim` |
| **`min`** | **Устанавливает минимальное значение** ресурса. Для `Container` это минимум для одного контейнера. Если контейнер запрашивает меньше, Pod не будет создан. | `Container`, `Pod`, `PersistentVolumeClaim` |
| **`default`** | **Значение `limit` по умолчанию**, которое автоматически присваивается контейнеру, если он его не указал. Если поле не задано в `LimitRange`, Kubernetes может установить его автоматически, приравняв к значению `max`. | `Container` |
| **`defaultRequest`** | **Значение `request` по умолчанию**, которое автоматически присваивается контейнеру, если он его не указал. Если поле не задано, Kubernetes может установить его равным значению `default`. | `Container` |
| **`maxLimitRequestRatio`** | **Максимально допустимое соотношение** между `limit` и `request` для ресурса. Это помогает избежать слишком сильного "перекоса" и гарантирует, что запрос (`request`) не будет чрезмерно мал по сравнению с лимитом (`limit`). | `Container`, `Pod` |

### Как это работает на практике

Процесс применения правил `LimitRange` выглядит так:

1.  **Проверка при создании**: Когда вы пытаетесь создать Pod или PVC в namespace, контроллер `LimitRange` проверяет его спецификацию.
2.  **Применение значений по умолчанию**: Если в контейнере не заданы `requests` и `limits` для CPU или памяти, контроллер автоматически подставляет значения из полей `defaultRequest` и `default`, если они определены в `LimitRange`.
3.  **Валидация ограничений**: Контроллер проверяет, что запрошенные и ограниченные значения соответствуют правилам `max`, `min` и `maxLimitRequestRatio`.
4.  **Результат**: Если проверка пройдена, Pod создается. Если нет, API-сервер вернет ошибку `403 Forbidden` с подробным объяснением.

### 💡 Важные нюансы

При работе с `LimitRange` стоит помнить о нескольких моментах:

*   **Проверка только при создании**: `LimitRange` проверяет ресурсы только в момент создания или обновления Pod'а. Изменение правил `LimitRange` не повлияет на уже работающие Pod'ы.
*   **Несколько LimitRange**: Если в namespace существует несколько объектов `LimitRange`, то, какое именно значение по умолчанию будет применено, **недетерминировано**. Поэтому лучше использовать только один `LimitRange` на namespace.
*   **Конфликт значений по умолчанию**: `LimitRange` не проверяет согласованность значений по умолчанию. Например, если установить `defaultRequest: 700m`, а `default: 500m` (лимит меньше запроса), то Pod получит эти значения и не сможет быть запланирован из-за ошибки `must be less than or equal to cpu limit`.
